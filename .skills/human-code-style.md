# Skill: Human Code Style (Anti-AI)

## Purpose
Write code that looks like it was written by a real developer — not generated by AI.
This matters because judges can ask any team member to explain any line of code.
Code should feel owned, not copied.

---

## What AI-Generated Code Looks Like (AVOID THIS)

### ❌ Over-explained comments
```cpp
// This function reads the temperature from the DHT11 sensor
// and returns the value in Celsius as a float
// It uses the DHT library to interface with the sensor
float readTemperature() {
  // Read the temperature value from the sensor
  float temp = dht.readTemperature();
  // Check if the reading is valid
  if (isnan(temp)) {
    // If the reading failed, return -1 as an error indicator
    return -1;
  }
  // Return the temperature value
  return temp;
}
```

### ✅ How a real developer writes it
```cpp
float readTemperature() {
  float t = dht.readTemperature();
  return isnan(t) ? -1 : t;
}
```

## Rules for Writing Code

### Comments
- Comment **why**, not **what**
- If the code is obvious, no comment needed
- Use comments for non-obvious decisions only

```cpp
// ❌ Bad
// Loop through all sensors
for (int i = 0; i < 3; i++) { ... }

// ✅ Good (only if actually needed)
// retry 3 times before marking sensor dead
for (int i = 0; i < 3; i++) { ... }
```

### Variable Names
- Short but meaningful
- No `myVariable`, `tempVariable`, `dataValue`

```cpp
// ❌ Bad
float temperatureValue = dht.readTemperature();
bool flameDetectedStatus = !digitalRead(FLAME_PIN);

// ✅ Good
float temp = dht.readTemperature();
bool flame = !digitalRead(FLAME_PIN);
```

### Functions
- Do one thing
- Name says exactly what it does
- No `doStuff()`, `handleEverything()`, `processData()`

```cpp
// ❌ Bad
void handleSensorDataAndSendToCloudAndUpdateDisplay() { ... }

// ✅ Good
void postSensorData(float temp, float hum, bool flame) { ... }
void updateLocalPage(float temp, bool door) { ... }
```

### No Filler Code
- No empty catch blocks just to suppress errors
- No `// TODO: implement this later` left in submission
- No disabled code blocks commented out in final submission

```cpp
// ❌ Bad
try {
  connect();
} catch (Exception e) {
  // handle error
}

// ✅ Good
if (!connect()) {
  Serial.println("WiFi failed, entering offline mode");
  offlineMode = true;
}
```

### Struct Over Chaos
Group related data:

```cpp
// ❌ Bad
float sensorTemp;
float sensorHum;
bool sensorFlame;
unsigned long sensorLastRead;

// ✅ Good
struct SensorData {
  float temp;
  float hum;
  bool flame;
  unsigned long lastRead;
};
SensorData sensor;
```

## Git Commits

Write commits like you're telling a teammate what changed:

```
❌ Bad commits:
"fix"
"update code"
"changes"
"final version"
"final version 2"

✅ Good commits:
"add DHT11 read with retry on NaN"
"fix flame sensor pin polarity (active LOW)"
"post sensor data to /api/sensor every 5s"
"SmartProv: add Room ID and class time fields"
```

**Format:** `<verb> <what> <why/where if needed>`

---

## File Organization
- One responsibility per file
- Filename matches what's inside
- No `utils.cpp` with 300 unrelated functions

---

## Before Submitting Any Code
- [ ] Can you explain every line without looking it up?
- [ ] Are there any comments that just restate the code?
- [ ] Are there any variable names you wouldn't use if a senior dev was watching?
- [ ] Does every function do exactly one thing?
- [ ] Are there any dead/commented-out code blocks?
